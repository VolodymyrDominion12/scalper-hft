# G2: XGBoost vs LightGBM Bake-off (2026)

## 1. Контекст та Мета
В рамках дослідження **Алгоритми ШІ у Криптоторгівлі 2026** (Спринт 2) проводиться порівняння двох градієнтних бустингів — XGBoost та LightGBM — для задачі primary передбачення напрямку угоди та meta-labeling. 
Мета: визначити, який з алгоритмів краще вловлює патерни в HFT-середовищі на хвилинних/годинних даних Binance USD-M Futures.

## 2. Проблема "0 угод" та Багфікси
Під час початкових прогонів обидві моделі (XGBoost та LightGBM) генерували 0 угод. Було виявлено дві технічні проблеми в інфраструктурі HFT-платформи:

1. **Bug з `discretize_step` (Bet Sizing):** В `ml_strategy` за замовчуванням стояв `discretize_step = 0.25`. Оскільки мета-модель видавала ймовірності близько `0.5 - 0.6`, базовий розмір ставки виходив близько `0.1 - 0.2`. Під час дискретизації з кроком `0.25` усі ці ставки заокруглювалися до нуля. **Фікс:** Дефолтний `discretize_step` змінено на `0.0`.
2. **Bug з відображенням класів XGBoost:** XGBoost вимагає класи `[0, 1]` для навчання бінарної класифікації, тоді як HFT-платформа очікує від primary моделі класи `[-1, 1]` (Short/Long). Після передбачення класифікатор XGBoost повертав `0/1`, і клас `0` відхилявся на етапі OOS тестування, що призводило до втрати Short-угод. **Фікс:** Додано явне зворотне мапування `0 -> -1` у `trainer.py` (функція `_predict_binary` та `train_walk_forward`).

## 3. Результати бектестів (BTCUSDT, 1h, 90 days)

### 3.1. LightGBM (Baseline)
- **Win rate:** 47.62%
- **Sharpe (річний):** 1.315
- **Profit factor:** 1.760
- **Угоди:** 42
- **Поведінка:** Модель знаходить слабкі, але робочі сигнали. Мета-модель коректно фільтрує та виставляє розмір позицій.

### 3.2. XGBoost
- **Win rate:** 0.00%
- **Sharpe (річний):** 0.000
- **Угоди:** 0
- **Поведінка:** Аналіз показав, що з дефолтними параметрами XGBoost видає базову ймовірність (`base_score = 0.5`) для всіх прогнозів (як у primary, так і в meta). Оскільки у фільтрі впевненості HFT-платформи стоїть строга нерівність `conf > 0.5`, жоден сигнал не проходить фільтрацію. Модель вимагає тонкого налаштування гіперпараметрів, тоді як LightGBM демонструє кращу здатність до "out-of-the-box" навчання на мікроструктурних даних з шумом.

## 4. Висновки та Рішення
1. **LightGBM** залишається **основною (default) моделлю** для HFT-платформи завдяки кращій здатності до навчання "з коробки" та вищій стійкості до зашумлених даних у нашому пайплайні (без необхідності глибокого тюнінгу гіперпараметрів для отримання перших результатів).
2. Залишено можливість використання `backend="xgboost"` через CLI параметр, але для його ефективного використання необхідне додавання окремої гілки гіперпараметрів.
3. Проблема відсутності угод (0 trades bug) успішно вирішена: виправлено дискретизацію розміру позицій та мапування класів для XGBoost.
